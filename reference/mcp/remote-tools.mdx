In remote mode (`action-platform mcp --remote`), your AI agent gets **36 tools** that act on apps running on your hosted Hub instance. Every call is authenticated with the JWT issued by `action-platform login` and sent as a `Bearer` token to `/api/v1/*`, where Hub's gate enforces your role, token scope, and reach.

## Prerequisites

Log in before starting the MCP server:

```bash
action-platform login https://<your-platform>
```

Use `--scope` to limit what the token (and therefore your agent) can do:

```bash
action-platform login https://<your-platform> --scope read           # read-only assistant
action-platform login https://<your-platform> --scope read,write,release  # ships, but cannot manage org
```

<Note>
  The remote MCP server automatically sends the MCP client's name
  (`clientInfo`) with every authenticated request. Hub's **Connected apps**
  view uses this to show whether a token was used by Claude Code, Codex,
  Cursor, or another MCP client — so you always know which AI agent made a
  change.
</Note>

## Editing workflow

Modifying an app's configuration follows a three-step loop that mirrors the Hub
web UI:

1. **Modify the workspace** — call `write_manifest`, `set_cloud`, and/or
   `add_service` as needed. Each call updates the workspace but does not commit.
2. **Commit** — call `commit_changes`.
   - If the workspace is on a protected branch, Hub automatically creates a new
     `<kind>/<code>` branch (using `branch_kind` + `branch_code` parameters).
   - Pass `pull_request=true` to push the branch and open a PR in the same
     call.
3. **Review** — use `gitflow_audit` or `propose_pull_request` if you want the
   agent to validate the change before it merges.

Hub's `/api/v1` proxy injects the organization's code-host credentials, so
private repositories, pushes, and pull requests all work without any additional
token on the client.

## Safe-by-default

`release` and `deploy` always default to `dry_run=true`. Your agent will show
you the outcome of the dry run and ask for explicit confirmation before calling
either tool with `dry_run=false`.

## Permissions reference

A call is allowed only when **all three** gates pass:

| Gate | What it checks |
|---|---|
| **Role** | Your role in the organization: `viewer`, `developer`, `deployer`, `admin`, or `owner` |
| **Scope** | The token's scope: `read`, `write`, `release`, or `admin` |
| **Reach** | Whether the token is limited to one organization, project, or app |

A refused call always names the missing permission or scope so you know exactly
what to change.
